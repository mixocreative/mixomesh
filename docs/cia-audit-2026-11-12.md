## For the owner, in five lines

mixoMesh is in good shape. It has the capability check, the error handling and the independent-reader
export proof its sibling app lacks, and a full morning of driving it produced **no console error and no
corrupted file**. Three things need you. **One: a textured model with UV seams — which is every model
this app exists for — is reported as full of holes, the Repair button cannot clear it, and with "strict
export" ticked the export is refused outright.** I proved this on your own test cube, which PrusaSlicer
and trimesh both call watertight. **Two: if recovering an autosave fails once, the code deletes that
autosave for good** — the only copy of the unsaved work goes with it. **Three: a project whose supports
record is damaged opens with a green "Loaded" and the supports silently gone**, with only a line in the
developer console. Everything else is MEDIUM or below.

### Context profile (`doctrine.md` §3 → `context-templates.md` §4a, creative / editor tool)

- **Software type** — interactive desktop + web editor, document-centred, single user.
- **State scope** — the scene in memory, the undo stack, view and tool state, per-user preferences.
- **Concurrency** — one UI thread, 11 Web Workers (`src/core/workers/`), GPU uploads, async file I/O.
- **Persistence** — `.mixo` (JSON + embedded bytes), autosave to IndexedDB/desktop KV every 60 s, exports
  to OBJ / 3MF / STL / PLY / WRL.
- **External dependencies** — the file system, GPU and driver limits, two vendored WASM engines
  (mixo-geocore, MeshFixLib), independent producers and consumers of its formats, Cults3D (publish).
- **Failure tolerance** — "the user's work is never lost"; every long operation cancellable.

**Primary quantity, named before grading anything:** *the scene the user is preparing and the file it
exports* — what the viewport shows, what the undo stack restores, what the saved `.mixo` reopens to, and
what the exported OBJ / 3MF / STL / PLY / WRL contains. Every grade below keys on that and on
irreversibility.

### Invariant register (`doctrine.md` §8.0) — every finding names one by number

1. The exported file contains every part, transform, material, UV and shell the viewport shows.
2. The saved `.mixo` reopens to the scene the user saw, or says exactly what it could not restore.
3. The user's unsaved work is never destroyed by the application itself.
4. A verdict the app prints about geometry agrees with what an independent reader sees in the same bytes.
5. A repair either changes the geometry and says what it changed, or reports that it changed nothing.
6. A control's scope is the scope its label claims.
7. Every job reaches a terminal state, or appears on a surface a person opens.
8. An export either produces the files the user asked for, or refuses with a reason that names the cause.
9. A green gate means the code it guards was exercised, against the real artefact, in the environment it ships to.
10. The renderer never receives an OS path; every file reference crossing the Electron boundary is an opaque token.

### MX-01 — A UV seam is counted as a hole, so a watertight textured model is reported broken, Repair cannot clear it, and strict export refuses it

> **CLOSED 2026-11-12.** The weld went into `MeshRepair.diagnoseMesh` itself, not into the one
> call site: `diagnose` now answers the position-welded topology, which is the question
> `repairObject` already acts on (its stage 1 merges duplicate positions). That covers all three
> raw-mesh diagnose callers at once — `MeshValidator.validateMesh:537`, `PrintPipeline._tryRepair`
> (whose C1 "leave a healthy clone alone" skip could never fire for a textured part) and
> `PrintPipeline._refreshRepairVerdict` (the post-CSG verdict the strict gate reads) — which is the
> S18 Rule 1 re-walk. `repairMesh` and `RepairSession.applyGeometryFix` keep passing RAW geometry
> on purpose: the engine merges for itself and `arraysToMesh` needs the original UVs to put back.
> `GroupRepair._buildUnion` was checked and already welds, so the group path needed nothing.
> Guards: `tests/diagnose-weld-mx01.test.mjs` (the real fixture geometry against an independent
> edge counter) and a validateMesh case in `tests/validator.test.mjs`.

- **Severity: HIGH** · **Confidence: CONFIRMED** (runtime artefacts from this session)
- **VSM System:** 3\* → 3 (the audit channel reporting on control state)
- **Domain:** State Management & Data Integrity
- **Defect class:** sampled where it should have been enumerated (S18 rule 1) + corner disagreement (S15) + vacuous failure (S21 shape 14)
- **Boundary location:** `MeshValidator.validateMesh (own welded topology) → engineDiagnose (unwelded engine diagnose)`
- **Invariants broken:** 4 (a verdict agrees with an independent reader), 5 (a repair says what it changed), 8 (a refusal names the cause)

**Evidence.** `src/core/MeshValidator.js:527` runs the validator's own topology check, which welds by
position first — the module comment at `:32-37` says why:

```js
 * always unwelded — each triangle carries its own vertex copies split for
 * as non-manifold even on a perfectly closed mesh. Welding by position first
```

Ten lines later, `src/core/MeshValidator.js:537` asks the repair engine the same question and does
**not** weld:

```js
      const { diag } = await engineDiagnose(mesh);
```

`engineDiagnose` (`src/core/repair/Diagnose.js:31-34`) passes the live mesh straight through. The two
checks on one mesh then disagree, and the engine's answer is the one that becomes the `holes` result.

**The team already found and fixed this exact class on the other route.** `src/core/MeshValidator.js:363-366`:

```js
 * two materials reported "16 holes" (measured live 2026-09-18). _topology
 * welds internally already; the engine diagnose did not.
```

and `:376` welds before the group diagnose — `const { positions, indices } = weldArrays(raw.positions, raw.indices);`.
The single-part route at `:537` was never re-walked. That is S18 Rule 1 verbatim: the instance was
fixed, the class was not.

**Observed behaviour (OBSERVED, this run).** `tests/fixtures/midtone-cube.glb` is a closed 20 mm cube —
the project's own independent consumers say so (`tests/consumers.mjs` `TRUTH.mid`: trimesh
`watertight: true`, PrusaSlicer `manifold: yes`, volume 8000 mm³). Its 12 triangles use 24 vertices
because every cube edge is a UV seam. Dropped into the running app:

```
MeshValidator.validateMesh  → [{ type:'holes', severity:'warning',
                                 message:'24 open edges (holes) — Auto-Fix fills them' }]
RepairSession.repairObject  → { applied:['holes'], holesFilled:0, nmFixed:0,
                                remaining:[{ type:'holes', count:24, fixed:false,
                                             autoFixAvailable:true }] }
                              geometry unchanged: 24 verts / 12 tris / identical bbox / UV kept
strictExport = true,
collectExportFiles(['stl']) → { blocked:true, code:'EXPORT_BLOCKED',
                                issues:[ geometry-warning,
                                         { code:'watertight-required', severity:'error' },
                                         below-bed ] }
```

**Failure scenario.**
1. A user imports any textured model — which, for a Mimaki UV-inkjet target, is every model.
2. The validation strip shows "⚠ N warning(s) — click to Repair"; the outliner shows a Repair pill.
3. They click Repair. It runs, fills 0, and the identical warning comes back with the Auto-Fix button
   still offered. There is no way for them to clear it.
4. They tick "Block export on non-watertight parts (strict)" — the one control that exists to protect a
   print — and the export is refused on a model that is correct.

**Impact.** The app's central case is mis-reported. The non-strict export is still correct (I proved the
3MF, STL and PLY all carry the right 12 triangles), so **no bad file is produced** — the damage is to
the instrument and to the gate: a permanently un-clearable alarm trains the operator to ignore every
alarm (S21 shape 14), and strict mode blocks correct work. The good news, worth stating because I
expected the opposite: **Repair does not damage the geometry.** Positions, triangle count, bounding box
and UVs were byte-identical afterwards.

**Recommended fix.** Weld before the single-mesh diagnose, exactly as the group path at `:376` already

### MX-13 — A throw anywhere in `bootstrap()` leaves a half-initialised app with autosave never started

- **Severity: MEDIUM** · **Confidence: HIGH-CONFIDENCE** (from code; not reproduced — injecting a boot throw is an application edit, which this run does not make)
- **VSM System:** 5 (policy on the boot path)
- **Domain:** Failure handling
- **Defect class:** partial initialisation with a cosmetic surface (S22)
- **Invariant broken:** 3 (the user's unsaved work is never destroyed by the application itself)

**Evidence.** `src/app/main.ts:57-63` states the intent:

```
// Failure = one blocking screen naming the problem, never a half-booted app.
```

That holds for `gateStorage()`, which returns before anything initialises. It does not hold for
`bootstrap()`, which is 25 sequential `.init()` calls (`:85-190`). A throw at any of them lands in the
catch at `:230-239`, which appends a div to `#viewport` — `.boot-status-overlay`,
`position:absolute; inset:0` on the viewport only (`src/styles/layout.css:105-141`). The header, the
outliner and the right panel stay live and clickable.

`AppShell.init()` at `:134` removes `#boot-status`, so from that point the last-resort handler in
`src/app/entry.js:23` is a no-op too. `PersistenceManager.startAutosave()` is at `:163` — a throw
anywhere between `:134` and `:163` leaves an app the user can type in with **no autosave running and no
signal that none is running**. The autosave liveness work (`AUTOSAVE_PAUSED_AFTER_SKIPS`,
`EVENTS.AUTOSAVE_FAILED`) detects a *stalled* autosave; it cannot detect one that never started.

**Mitigation that holds.** `wireCloseFlow()` is at `:132`, before `AppShell.init()`, so the dirty-close
guard is installed for every throw after that point and the user is at least warned on close.

**Recommended fix.** Start the autosave timer early (right after `PersistenceManager.init()` at `:131`),
and make the `bootstrap()` catch render the full-screen blocking message rather than a viewport overlay
— the app is not usable in that state and should not look as if it is.

**CLOSED 2026-11-12** (plan §5.2). The `bootstrap()` catch now renders the same full-screen
`renderBlockingMessage` as the gates, with `data-reason="bootstrap"`, and `.boot-status-overlay` is
deleted. Reproduced live first by `tests/browser-boot-gate.mjs`'s third pass (#viewport removed from
outside the app, so one real `.init()` throws): **159 pressable controls and a live outliner before,
0 and none after**. The autosave half of the recommendation is not needed by this route — the blocking
screen empties `<body>`, so there is no app left to type unsaved work into — and is therefore
deliberately not taken; a *boot that succeeds* and then loses autosave is a different fault and has no
evidence here. Same commit also added the GPU probe (§5.1) this catch used to absorb.

## The final cybernetic question

> *If the viewport, the in-memory scene, the undo stack, background workers, GPU buffers and the file on
> disk disagree, does mixoMesh know which is authoritative, and can it save, undo and recover without
> losing the user's work?*

**On the file: yes.** I drove one model through all four corners and they agreed to the triangle, and the
project proves its own output against readers that share no code with it.

**On the verdict: no.** Two checks inside one function disagree about whether the user's geometry is
closed, the app believes the wrong one, and the only remedy it offers does nothing (MX-01).

**On recovery: not yet.** The one path that exists to give the user their work back deletes it if it
fails once (MX-02), and a load can drop their hand-placed supports behind a success toast (MX-03).

Fix those three and the answer is yes.
